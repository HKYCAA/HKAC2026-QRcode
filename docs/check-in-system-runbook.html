1. Architecture and data flow

Phone camera or manual entry
GitHub Pages frontend
Apps Script doPost
Google Sheet
  1. html5-qrcode scans locally in the phone browser.
  2. The frontend extracts only the unique code and displays it in the input field. Scanning alone does not record attendance.
  3. The operator reviews the code and presses Check in.
  4. The frontend sends a form-encoded POST request to Apps Script.
  5. Apps Script finds an exact code match, prevents duplicates, writes attendance, timestamps the roster row, and colors it green.

2. Google Sheet rules

Source tab: all

Field Purpose Write rule
Code Unique student code generated by an array formula Never write to or clear this column.
Chi+Eng Preferred student display name Read only
Timestamp Arrival date and time Written on check-in; cleared on undo
Student row background Visible checked-in state Set to saturated green #81c995 on check-in; cleared on undo

Attendance tab: qrcode-scan

The header order is a backend contract and must remain:

Timestamp | Code | Name | Source Row
Do not rename or reorder these four log headers. Apps Script deliberately rejects an unexpected schema instead of writing attendance into the wrong columns.

3. Frontend scanner behavior

  • Requests the rear camera with { facingMode: "environment" }.
  • Supports raw payloads such as YDQ0621 Chinese Name English Name by taking only the first whitespace-separated token.
  • Supports QR URLs containing a code query parameter.
  • Trims and uppercases the code before submission.
  • Places scans in the input and flashes it green so the operator notices when a new QR code replaces the previous one.
  • Requires the operator to press Check in; it never auto-submits a scan.
  • Snapshots the submitted code before sending it. A new scan can appear while the previous request is processing without changing the code already being submitted.
  • Shows the exact in-flight code on the button: Submitting YDQ0621….
  • Keeps the camera running during network requests so the next QR code can be prepared.
Wrong-submission protection Manual confirmation, the flashing input, the in-flight code on the button, exact backend matching, and duplicate detection work together. Do not remove one of these protections merely to save a tap.

4. Apps Script backend behavior

The production backend is the standalone qrcode-scan Apps Script project. It exposes one doPost entry point and executes as the deployment owner.

Successful check-in

  1. Normalize and validate the request.
  2. Open the spreadsheet by its fixed ID.
  3. Verify the source and log tabs exist.
  4. Verify the exact attendance log schema.
  5. Locate the Code and preferred name headers.
  6. Find an exact, case-insensitive, whole-cell code match.
  7. Acquire the script lock.
  8. Reject a duplicate found in qrcode-scan.
  9. Append the attendance log entry.
  10. Write the same time to the roster Timestamp cell and color the populated student row green.

Undo

Undo finds the active log entry, deletes it, uses its stored Source Row to locate the roster student, clears the roster timestamp, and removes the green background.

Response contract

Status Meaning Frontend message
success Attendance recorded Successfully checked in, code and name
duplicate Code already exists in the log Already checked in
invalid No exact roster match Invalid code
undone Attendance and roster state removed Check-in undone
error Configuration, permission, lock, or server failure Unable to check in

5. Key findings and mistakes to avoid

Confirmed: compact camera CSS broke iPhone scanning

The iPhone Safari camera preview remained visible, but QR callbacks stopped after aggressive one-screen mobile styling changed the scanner/video geometry. Rolling back those compact UI rules restored scanning.
  • Keep #reader with a real minimum height and allow the library to manage the video’s natural dimensions.
  • Keep the scanner aspectRatio: 1 and calculate qrbox from the actual viewfinder dimensions.
  • Do not force the scanner video into a tiny fixed-height container.
  • Do not add aggressive object-fit, transforms, clipping, or repeated width/height overrides without testing real iPhone Safari scanning.
  • A visible preview proves camera permission and playback only. It does not prove QR frame detection works.

Confirmed: scanner callbacks must not submit automatically

A QR payload can include both the unique code and names. The safe design extracts the first token, shows it to the operator, and waits for confirmation. Submitting the full QR text will fail exact matching.

Confirmed: do not pause the camera during a POST

Pausing after every check-in adds delay and extra clicks. Keep the camera active, but snapshot the code being submitted so a subsequent scan cannot alter the in-flight request.

Confirmed: Apps Script deployment version matters

clasp push updates project source but does not by itself move the fixed production web-app deployment to the new version. Update the existing deployment ID after every backend change.

Confirmed: Google redirect handling can mislead command-line tests

For an Apps Script POST smoke test, use curl -L --data without forcing -X POST. Forcing POST across Google’s redirect can return a generic Drive “Page not found” page even when the deployment is healthy. 

curl -sS -L \
  --data 'action=checkin&code=CODEX-SMOKE-INVALID' \
  'https://script.google.com/macros/s/DEPLOYMENT_ID/exec'

Suspected, not proven: mixed browser cache after Pages updates

A temporarily broken button was consistent with cached GitHub Pages assets, but the cache hypothesis was not proven and no cache-busting change was deployed. First hard-refresh or reopen the site and inspect the loaded HTML/JavaScript versions before changing working logic.

6. Safe testing checklist

Before every deployment

npm test
npm run check
git diff --check
git diff
clasp status
clasp show-authorized-user

Functional checks

  • Android rear camera opens and recognizes a valid QR.
  • iPhone Safari preview opens and recognizes a valid QR.
  • QR code plus names produces only the leading unique code.
  • A second scan replaces and flashes the input.
  • No attendance is recorded until Check in is pressed.
  • The button shows the code currently being submitted.
  • A valid check-in returns code first, then student name.
  • The roster timestamp is populated with arrival date/time.
  • The full populated roster row becomes green.
  • A duplicate reports Already checked in and adds no second log.
  • An invalid code adds no attendance record.
  • Undo removes the log, timestamp, and green highlight.
  • The array-formula Code column remains unchanged.
Never use a real student code for an unattended smoke test. Use a deliberately impossible code and expect {"status":"invalid","message":"Invalid code"}. A real code changes live attendance.

7. Deployment process

Backend: Google Apps Script

  1. Confirm .clasp.json points to the dedicated qrcode-scan project.
  2. Confirm the authorized Google account.
  3. Review exactly which files clasp will upload.
  4. Push the source.
  5. Update the existing production deployment ID; do not create a new public URL unless intentionally migrating the frontend.
  6. Confirm clasp deployments shows the new version.
  7. Run only the invalid-code production smoke test.

Current production Apps Script deployment is version 6 at the time this runbook was written.

Frontend: GitHub Pages

  1. Run tests and syntax checks.
  2. Commit only the intended files.
  3. Push main to the GitHub repository.
  4. Wait for GitHub Pages to publish.
  5. Reopen the live HTTPS site and test on both Android and iPhone Safari. Do not rely on desktop camera emulation.
If a backend deployment URL ever changes, update config.js before publishing the frontend. Otherwise the site will continue calling the old Apps Script deployment.

8. Troubleshooting and recovery

Symptom Check first Safe response
Camera preview visible but no scan on iPhone Recent scanner/video CSS and actual Safari behavior Revert geometry changes to the last known working scanner layout; retain natural video sizing and aspectRatio: 1
Manual Check in button appears inactive Whether a normalized code exists and whether a request is active Hard-refresh first, then inspect the loaded asset versions and syncSubmitAvailability()
“Unable to check in” for every code Network, Apps Script URL, deployment version, and authorization Run the invalid-code curl smoke test and review Apps Script logs
Valid student reported invalid Exact Code value and header name Compare normalized code with the displayed sheet value; never loosen matching to partial text
Duplicate check-ins appear Script lock and qrcode-scan Code column Preserve duplicate checking and the lock around check-and-write
Roster row remains green after undo Stored Source Row and roster Timestamp Verify the log schema and undo response before editing the row manually

Rollback rule

Roll back the smallest responsible layer. A camera regression should first revert scanner/UI geometry, not the attendance backend. A sheet write regression should update Apps Script, not the working camera layout. Re-run the same device-specific test after rollback.
